1 1. The join commands, and the two protective arguments

The mutating joins all take the form *_join(x, y, by = ...):

  • left_join() — keeps every row of x, fills with NA where y has no match. The default choice.
  • inner_join() — keeps only rows present in both.
  • right_join() — keeps every row of y.
  • full_join() — keeps every row of both.

The filtering joins do not add columns, they only subset x:

  • semi_join() — keeps rows of x that have a match in y.
  • anti_join() — keeps rows of x with no match. Excellent for finding what is missing.

The two arguments that prevent mistakes:

  • by — always state the key explicitly. A natural join on every shared column name is rarely what you want, and it changes silently when someone adds a column.
  • relationship — declare what you expect ("one-to-one", "many-to-one", and so on). dplyr then errors if the data disagrees, instead of quietly producing extra rows.

2 2. Joining baseline to mortality

joined <- left_join(baseline, mortality, by = "participant_id")

c(baseline = ncol(baseline), mortality = ncol(mortality), joined = ncol(joined))
 baseline mortality    joined 
       73        22        94

2.1 2a.

73 + 22 would be 95, but the result has 94. The key participant_id appears once rather than twice, so we lose one column.

2.2 2b.

sum(grepl("\\.x$|\\.y$", names(joined)))
[1] 40

The two tables share 20 column names besides the key — age_years, sex_at_birth, frailty_category and so on. dplyr cannot have two columns with the same name, so it suffixes both copies.

What to do about it: select() only the columns you actually need from the second table before joining. Carrying 20 duplicated columns around is how you end up analysing age_years.y by accident.

tidy_join <- baseline |>
  left_join(select(mortality, participant_id, died_during_followup, age_at_death),
            by = "participant_id")

ncol(tidy_join)
[1] 75

3 3. The join that changes your row count

3.1 3a and 3b.

visit2 <- filter(visits, visit_number == 2)

joined_v2 <- left_join(baseline, visit2, by = "participant_id")

c(before = nrow(baseline), after = nrow(joined_v2))
before  after 
  2400   2402

You would expect 2,400 — one row per participant. You get 2,402.

3.2 3c.

visit2 |>
  count(participant_id) |>
  filter(n > 1)
# A tibble: 2 × 2
  participant_id     n
  <chr>          <int>
1 BIO00010           2
2 BIO00018           2

Two participants have their visit-2 record entered twice. They are exact duplicates:

dupes <- visits |>
  filter(participant_id %in% c("BIO00010", "BIO00018"), visit_number == 2)

c(rows = nrow(dupes), distinct_rows = nrow(distinct(dupes)))
         rows distinct_rows 
            4             2

Each of those two participants therefore matches two rows in visit2, and left_join() duly returns both.

3.3 3d.

left_join(baseline, visit2, by = "participant_id", relationship = "one-to-one")
Error in `left_join()`:
! Each row in `x` must match at most 1 row in `y`.
ℹ Row 10 of `x` matches multiple rows in `y`.

It errors immediately and names the offending row. This is a better failure because it happens at the join, where the cause is obvious, rather than surfacing three steps later as a mean that is slightly wrong in a way nobody can explain. Two extra rows in 2,400 will not look wrong in any summary you produce.

4 4. Reshaping the weights

4.1 4a.

wide_bad <- visits |>
  select(participant_id, visit_number, weight_kg) |>
  pivot_wider(names_from = visit_number, values_from = weight_kg, names_prefix = "visit_")
Warning: Values from `weight_kg` are not uniquely identified; output will contain
list-cols.
• Use `values_fn = list` to suppress this warning.
• Use `values_fn = {summary_fun}` to summarise duplicates.
• Use the following dplyr code to identify duplicates.
  {data} |>
  dplyr::summarise(n = dplyr::n(), .by = c(participant_id, visit_number)) |>
  dplyr::filter(n > 1L)
class(wide_bad$visit_2)
[1] "list"

The columns are list-columns, not numeric, and pivot_wider() warns that values are “not uniquely identified”.

4.2 4b.

The same two duplicated rows from question 3. pivot_wider() expects one value per participant per visit; for BIO00010 and BIO00018 at visit 2 it finds two, and rather than guess it wraps every cell in a list.

4.3 4c.

Because it is loud. pivot_wider() warns and hands back an obviously wrong data type, so you find out within seconds. left_join() said nothing at all. The same data problem, discovered immediately in one case and potentially never in the other — which is the whole argument for checking row counts yourself rather than relying on the function to tell you.

4.4 4d.

Since the duplicates are exact, distinct() is a defensible fix — we are removing a double-entered record, not choosing between two conflicting measurements:

wide <- visits |>
  select(participant_id, visit_number, weight_kg) |>
  distinct() |>
  pivot_wider(names_from = visit_number, values_from = weight_kg, names_prefix = "visit_")

c(rows = nrow(wide), cols = ncol(wide))
rows cols 
2400    7 
class(wide$visit_2)
[1] "numeric"

Had the two rows disagreed on weight, distinct() would not have helped and the right answer would have been to go back to the source and ask which is correct. Record whichever you did, and why.

5 5. Back to long format

long <- wide |>
  pivot_longer(
    -participant_id,
    names_to = "visit",
    values_to = "weight_kg",
    values_drop_na = TRUE
  )

c(rows = nrow(long), if_complete = 2400 * 6)
       rows if_complete 
      10730       14400

10,730 rather than 14,400, because the study has attrition: participants miss visits, withdraw, or die, so most people do not have all six measurements. values_drop_na = TRUE discards those empty cells.

6 6. across()

6.1 6a.

baseline |>
  summarise(across(c(bmi_kg_m2, systolic_bp_mmHg), ~ mean(.x, na.rm = TRUE)))
# A tibble: 1 × 2
  bmi_kg_m2 systolic_bp_mmHg
      <dbl>            <dbl>
1      28.3             140.

6.2 6b.

baseline |>
  summarise(
    across(
      c(bmi_kg_m2, systolic_bp_mmHg),
      list(mean = ~ mean(.x, na.rm = TRUE), median = ~ median(.x, na.rm = TRUE))
    )
  )
# A tibble: 1 × 4
  bmi_kg_m2_mean bmi_kg_m2_median systolic_bp_mmHg_mean systolic_bp_mmHg_median
           <dbl>            <dbl>                 <dbl>                   <dbl>
1           28.3             28.1                  140.                     139

6.3 6c.

baseline |>
  group_by(imd_quintile) |>
  summarise(
    across(c(bmi_kg_m2, systolic_bp_mmHg), ~ round(mean(.x, na.rm = TRUE), 1)),
    n = n()
  )
# A tibble: 6 × 4
  imd_quintile bmi_kg_m2 systolic_bp_mmHg     n
         <dbl>     <dbl>            <dbl> <int>
1            1      27.4             140.   460
2            2      28.1             138.   486
3            3      28.2             142.   476
4            4      28.8             140.   492
5            5      28.9             141.   485
6            9      25.3             129      1

There are six groups, not five. IMD quintiles run 1 to 5, so the single participant coded 9 is an invalid value — most likely a data entry error or a missing-value code that was never translated.

Grouping is a good way to find these: an unexpected group with a tiny n almost always means a coding problem rather than a real subgroup. Note also that a group of one gives you a “mean” with no spread at all, which will look perfectly reasonable in a summary table.
